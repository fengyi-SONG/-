## 1. 产品定位（重新定义）

### 1.1 一句话

**帮"有素材但说不清"的学生，把一段真实经历整理成一份能被面试官追问的作品集。**

### 1.2 它不是什么（明确划界）

这一节比"它是什么"更重要，因为前几版的失败都来自边界模糊：

- ❌ **不是"AI 帮你写作品集"**。AI 不生成你的经历，只负责提问、纠正表述、检查事实状态。
- ❌ **不是"零素材也能出作品"**。零素材的人得到的是"去做一件真事"的行动路径，不是一份编出来的作品集。
- ❌ **不是通用岗位平台**。首期只把产品经理/AI 产品经理一条线做深，其他方向走基础流程。
- ❌ **不是排版工具**。排版是副产品，核心是"把话说清楚"。
- ❌ **不是简历生成器**。作品集讲"一个项目讲透"，简历讲"多段经历压缩"。

### 1.3 核心价值主张

```
输入：一段真实经历（哪怕是小课程作业、一次社团活动）
过程：被追问 10-20 个问题，其中一半你自己都没想到要回答
输出：一份标注了"哪些是事实、哪些是推断"的作品集
```

**关键差异点不是"快"，而是"诚实且经得起追问"。**

现有工具（模板站、简历工具、通用 AI 写作）的共同缺陷是：它们帮你把话**写得漂亮**，但没帮你判断**这话站不站得住**。面试第一轮追问"这个 38% 怎么算的"，漂亮话就崩了。

### 1.4 产品原则（按优先级排序，冲突时上位优先）

1. **不编造事实** —— 没有数据就不出现数字；推断必须标为假设
2. **不制造死路** —— 任何问题都能跳过，跳过记入缺口清单而非丢弃
3. **不让用户面对空白** —— 每个开放问题都有示例句式或可选项
4. **本地优先** —— 无后端、无账号、无埋点；数据不出浏览器
5. **拒绝虚假繁荣** —— 宁可作品集看起来"内容少但可信"，不要"内容丰富但一问就崩"

## 2. 目标用户

### 2.1 首期唯一主用户（收缩后）

> **在校生 / 应届生，找第一份产品经理或 AI 产品经理工作，手上有 0-2 段真实经历（课程项目、社团、比赛、短实习），但写不出作品集。**

特征：
- 有素材，但认为"这不值得写"（课程作业、社团活动被自己判定为不足）
- 一被要求"描述你的项目"就卡住，写出来是流水账
- 不知道面试官会问什么，因此不知道作品集该写什么
- 愿意花 1-2 小时，但不愿意花 10 小时学"怎么写作品集"

### 2.2 明确不服务的用户（首期）

| 用户 | 为什么不做 | 什么时候再做 |
|---|---|---|
| 零素材且不愿动手的人 | 唯一诚实的产品答案是"先去做一件事"，我们给路径但不代做 | 不做。这是产品底线 |
| 资深从业者（5 年+） | 他们需要的是叙事策略和个人品牌，不是引导问答 | 不做 |
| 设计/开发岗求职者 | 作品集的核心是作品本身（视觉/代码），不是文字组织 | 第二期，需独立设计渲染模板 |
| 需要投递管理/多版本管理的用户 | 属于 ATS 领域，与当前价值主张无关 | 不做 |

### 2.3 次期候选用户（【假设】，未验证）

- 转行者：有可迁移能力但缺对口经历，需要"翻译"能力
- 1-3 年产品经理换赛道

**为什么先不做**：这两类人的真实痛点我们只是推测，没有访谈数据。首期做窄，是因为窄才可能做深。

## 3. 核心问题与解决方式

### 3.1 问题清单（对齐诊断报告 P-1 ~ P-6）

| 编号 | 真实问题 | 现有产品为什么解决不了 | 本产品的解法 |
|---|---|---|---|
| P-1 | 用户不知道"什么值得写" | 模板站给结构不给判断 | 用追问暴露判断标准：每一题都说明"为什么问这个" |
| P-2 | 零素材用户被"造项目"诱导编故事 | 工具倾向于填满模板，因为空着难看 | 给"真做一次"的 1 周练习路径，明确不代编 |
| P-3 | 零经历用户在经历环节卡死 | 流程假设用户有经历 | 素材盘点为空时直接跳过整个经历区块 |
| P-4 | 数字随口编，面试就崩 | 工具鼓励"量化你的成果"，用户就凑数字 | 无数字就不出现数字；估算值标"约"；来源不明标"待补" |
| P-5 | 分不清"我做的"和"团队做的" | 没人问，用户也不主动写 | 贡献度强制拆分（独立/负责/协作/他人/AI 辅助） |
| P-6 | 作品集里哪些是事实、哪些是判断，读者不知道 | 输出物没有可信度信号 | 六态事实模型 + 页面级徽标（未验证/计划中/待补充） |

### 3.2 六态事实模型（本产品的核心机制）

每个可陈述内容都带一个状态：

| 状态 | 含义 | 页面表现 | 谁会看到 |
|---|---|---|---|
| `fact` 已确认事实 | 你亲自确认发生过、能说清来龙去脉 | 正常显示 | 读者无感知 |
| `evidence` 有材料支撑 | 有截图/文档/记录可查 | 正常显示 + 证据区块 | 读者可见证据列表 |
| `claim` 你的陈述（未核实） | 你说的，但没有材料 | 正常显示 | 导出前提醒补充 |
| `assumption` 待验证假设 | 推断、猜测、没验证的结论 | 带「未验证」徽标 | **读者直接看到** |
| `plan` 未来计划 | 还没做，打算做 | 带「计划中」徽标 | **读者直接看到** |
| `unknown` 信息不足 | 跳过或答不出 | 带「待补充」徽标 | 读者可见 |

**设计意图**：徽标不是给用户看的羞耻标记，是给**读者**的可信度信号。一份标了 3 处"未验证"的作品集，比一份看起来完美但经不起追问的作品集更可信。

### 3.3 数字防线（P-4 的具体实现）

**【已验证】** `parseMetric()` 的实测行为：

| 输入 | 结果 | 状态 |
|---|---|---|
| `41%→55%` | 解析为前值 41%、后值 55% | `claim` |
| `从30人涨到200人` | 解析为 30 人 → 200 人 | `claim` |
| `提升约30%` | 识别为 30%，追加 note「用户表述为估算值」 | `claim` |
| `不知道` | **不产出任何指标**，reason=`no-number` | — |
| `很多` / `不少` | **不产出任何指标** | — |
| `2023` | **不产出指标**（年份不是成果） | — |
| 空 | **不产出指标**，reason=`empty` | — |

**关键**：解析失败时返回 `{ok:false, reason}`，界面提示"你可以不填，系统不会替你生成"，而不是退回一个默认值。

## 4. 功能规格

### 4.1 系统架构（实况）

```
index.html（工作台：左问答 / 右预览）
    │
    ├── renderer.js      纯函数渲染：profile → 自包含 HTML 字符串
    ├── fact-core.js     事实状态数据层：六态模型 / 指标解析 / 迁移 / ledger
    ├── role-kit.js      岗位知识库：工具 / 方法 / 指标 / 练习路径 / 方法论卡
    ├── flow-engine.js   缺口驱动流程引擎：下一步是谁 / 答案写回 / 缺口清单 / 撤销
    ├── fact-panel.js    事实检查面板 UI
    ├── inline-edit.js   预览区就地编辑
    └── vendor/html2pdf  导出 PDF（本地打包）
```

**已删除**（v3.3 裁剪）：`wizard-engine.js`、`interview-engine.js`（共 75KB，v3.1 后已无引用）。

### 4.2 F1 缺口驱动问答引擎 【已验证】

**与旧版（字段驱动）的区别**：

- 旧版：按固定字段清单走，没有值就问 → 跳过=永久丢失 → 无经历用户被反复问同一题
- 新版：按"当前资料还缺什么、缺的这块值不值得问"决定下一步 → 跳过=记入缺口清单 → 永不重复问

**实测步骤序列**（零经历用户，【已验证】）：

```
name → track → roleText → stage → sourceInventory → pickPractice
→ projName → users → problem → evidence → analysis → approach
→ alternatives → contribution → result → validation → metrics
→ limitations → nextStep → evidenceList → projMore
→ skills → education → contact → review
```

注意：**`expOrg` / `expRole` / `expTime` / `expDetail` 完全未出现** —— 这是 P-3 的修复证据。

**有实习经历的 PM 用户**会多出经历区块（`expOrg → expRole → expTime → expDetail → expMore`），且在项目环节走完整的七模块。

**每个问题必须包含**：
- `why` —— 「为什么问这个」（产品原则 P-1 的落地）
- 示例句式或可选项（不允许裸空白输入框，除非是姓名这类唯一答案）
- 可跳过时显示跳过；不可跳过时说明原因

**撤销机制**：【已验证】从"profile 快照回滚"改为"answers 栈 + 按 stepId 显式清字段"，避免撤销后状态错乱（实测 34 项断言覆盖）。

### 4.3 F2 缺口清单（替代"跳过即丢失"）【已验证】

跳过的问题进入 `openGaps()`，在工作台底部以 chips 形式长期可见。点 chip 可直接回到该问题补答，补答后 chip 消失。

**语义修正**：跳过 = "现在答不上来，但我不假装它不存在"，不是"放弃"。

### 4.4 F3 岗位知识库与方法论卡 【已验证】

**产品经理 / AI 产品经理**（唯一深流程岗位）：

| 字段 | 内容 | 用在哪 |
|---|---|---|
| `tools` | 14 个常用工具 | 技能题选项 |
| `methods` | 10 个方法论/工作动作 | 技能题选项 |
| `metrics` | 7 个常用指标 | 仅作**参考**，不预填 |
| `practice` | 1 周产品分析练习（标题/周期/产出/5 步骤/3 类证据） | 零经历路径 |
| `playbooks` | 4 张方法论卡，每卡 7 问 | 分析/方案/指标题的下方提示 |

**方法论卡结构**（每卡必须答全 7 问，有测试守卫）：

`解决什么问题` / `适用场景` / `前提条件` / `怎么执行` / `产出证据` / `何时不适用` / `没有数据时怎么办`

现有 4 张卡：漏斗定位法、小样本访谈法、方案取舍法、指标口径法。

**智能选卡**：【已验证】分析题会读用户在"证据"题勾了什么 —— 勾了"有数据"推漏斗卡，勾了"访谈/问卷/亲身经历"推访谈卡。这是"AI 学会补充"的具体实现。

其他方向（运营/设计/数据/开发…）：走基础流程（5 步：用户 → 问题 → 方案 → 贡献 → 结果），无方法论卡。

### 4.5 F4 事实检查面板 【已实现·未验证】

入口：右上角「🛡 事实检查」（快捷键 `Ctrl+K`），按钮上带待确认数量角标。

面板按"最不可信优先"排序（`unknown < assumption < plan < claim < evidence < fact`），每项给 4 个动作：

| 动作 | 效果 |
|---|---|
| 确认属实 | status → `fact`（会二次确认：你确定能说清来龙去脉吗） |
| 补来源 | 填写材料链接/出处 → status → `evidence` |
| 标为假设 | status → `assumption`，页面显示「未验证」徽标 |
| 先不管 | 保持原状态，下次打开仍在列表 |

> **未验证部分**：面板的 DOM 交互逻辑在 Node 环境无法测，尚未在真实浏览器里完整点过一遍。这是已知缺口，列入验收待办。

### 4.6 F5 渲染与导出 【已验证】/【已实现·未验证】

**主题**：2 套（`aurora` 现代科技 / `paper` 编辑质感）。旧数据的 `mono`/`noir` 自动迁移到 `aurora`。

**项目卡结构**（PM 深流程产出）：

```
项目名 + 角色 + 周期
├─ 面向用户：谁 / 多大规模
├─ 背景：当时的情况
├─ 问题：谁在什么场景卡在哪
├─ 我的分析：排除过程
├─ 做法：方案与取舍
├─ 未采用的方案：考虑过但放弃的
├─ 我做了什么：贡献度表格（独立/负责/协作/他人支持/AI 辅助）
├─ 结果：做到哪一步 + 指标（带状态徽标）
├─ 局限：主动暴露的不足
├─ 下一步：计划中（带徽标）
└─ 证据材料：可查的记录列表
```

**【已验证】** 渲染层通过离线渲染 + 真实浏览器截图确认：徽标、贡献度表、证据区块、来源待补提示均正确显示。

**【已实现·未验证】** PDF 导出：html2pdf 生成 A4，`@page` + `break-inside:avoid` 已有，但**长文档分页、中文字体贴合、Safari 兼容三项均未实测**。

**导出前闸门**：【已验证】导出时先跑 `buildLedger()`，若存在 `unknown`/`assumption` 项则弹确认，引导先过事实检查。

### 4.7 F6 链接读取 【已验证，范围已收缩】

| 链接类型 | 行为 |
|---|---|
| GitHub 公开仓库 | 走 `api.github.com`，取仓库名/描述/语言/topics |
| 其他链接 | **不解析**，提示手动补充内容 |

**v3.0 声称的 `r.jina.ai` 通用网页代理已移除** —— 原因：把用户数据发给未声明的第三方，与隐私原则冲突且不可控。

### 4.8 F7 隐私与数据控制 【已验证】

三档数据流明示（`DATA_FLOW`）：

| 档位 | 内容 | 去向 |
|---|---|---|
| 本地处理 | 你填的所有内容、渲染、PDF 生成、本地存储 | 不出浏览器 |
| 链接读取 | 你粘贴的 URL、该 URL 的公开内容 | 仅 `api.github.com`，且需主动触发 |
| LLM（未接入） | — | 见 4.9 |

已具备的控制：
- 「删除本机全部数据」按钮（含二次确认）
- `beforeunload` 保护：有未保存内容时离开页面会提示
- 存储键带版本号（`pf.profile.v3` / `pf.ai.v3` / `pf.session.v3`）

### 4.9 F8 LLM 增强 —— 【已实现·已验证（mock 接口）】

**当前状态（v3.5）**：路线 A（用户自填 Key）已实现并经端到端验证：

- 「AI 设置」面板：接口地址 + Key + 模型名，仅存本机 localStorage，带「测试连接」
- 长文本题出现「✨ 让 AI 帮我改写」按钮 → 弹窗并排对比原文/改写文 → 用户确认才采用
- **AI 润色的答案提交后自动标 `status:'assumption'` + `by:'ai'`**，并进入事实检查清单等待用户确认——`assertClaim` 守卫保证 AI 内容永远无法直接成为 `fact`
- prompt 铁律：不新增事实/数字、不改数值、不把推断改写成结论、只输出正文
- 未配置 Key 时全部功能照常可用（LLM 是增强不是依赖）
- 验证：`tests/llm-e2e.js`（puppeteer + mock 接口，13 项断言），覆盖成功/未配置/401 错误/状态标记/入清单全链路

**尚未验证**：对真实 LLM 接口（DeepSeek 等）的实际调用效果——需要真实 Key，属人工目检项。

## 5. 数据结构（v3 schema）

```js
{
  meta: {
    version: 3, theme: 'aurora'|'paper', accent: '#rrggbb',
    track: 'pm'|'basic', stage: '', curProj: 0|null,
    noExp: bool, practice: 'starter'|'custom'|'skip',
    expDone: bool, projDone: bool, srcScanned: bool, sources: []
  },
  hero: { name, title, tagline, location, email, phone, links[], available, badge },

  projects: [{
    name, role, period, link, description,
    fields: {                       // 每个字段都带状态
      problem:{ text, status }, approach:{...}, result:{...}, context:{...}
    },
    users:        { who, scale, status },
    evidence:     ['data','interview','survey','self','desk','none'],
    contribution: { self:'owner'|'partial'|'support'|'unknown', team, ai, detail, status },
    alternatives: { text, status },
    limitations:  { text, status },
    nextStep:     { text, status },
    metrics:      [{ value, label, status, note }],
    evidenceList: [{ name, link, status }],
    decision:     { why, alternatives, status },
    validation:   ['interview','survey','usability','abtest','postlaunch','none']
  }],

  experiences: [{ org, role, start, end, current, context, highlights[], metrics[], tags[] }],
  skills:      { groups: [{ name, items: [string] }] },
  education:   [{ school, degree, major, start, end, note }],
  extras:      [{ title, detail }]
}
```

**迁移**：`migrate(profile)` 幂等，v2 → v3 时：
- 所有旧指标补 `status:'claim'` + `note:'由 v2 数据升级，来源待补'`
- 补齐缺失的 `contribution` / `users` / `evidenceList` / `limitations` / `nextStep` 结构
- `mono`/`noir` 主题归一为 `aurora`

**会话**（独立存储）：

```js
{ answers: [{ stepId, targetPath, outcome:'answered'|'skipped'|'unknown', at }],
  cursor: number }
```

## 6. 功能优先级

### 6.1 优先级判定标准

使用 **RICE 的简化版**，但只回答一个问题：**这一项不做，用户会不会在真实场景里卡住或说错话？**

| 级别 | 定义 | 处理 |
|---|---|---|
| **P0** | 不做就会导致用户产出不可信内容，或流程中断 | 必须做完才可对外 |

| **P2** | 提升体验，不影响正确性 | 二期 |
| **P3** | 需要先验证用户需求存在 | 待研究 |

## 7. 用户研究计划

### 7.1 现状说明（诚实前置）

**本项目至今没有做过一次真实用户访谈或可用性测试。** 本文档所有关于用户行为的描述，均为基于"常见求职场景"的推断，不是观察结果。

**这直接意味着**：第 2 章的用户画像、第 3 章的问题优先级，都建立在假设上。

### 7.2 待验证假设（与诊断报告 H1-H6 对齐）

| 编号 | 假设 | 如果为假，产品要怎么改 | 证伪成本 |
|---|---|---|---|
| H1 | 学生真正的痛点不是"不会排版"，而是"不知道自己做的事值不值得写" | 如果排版才是痛点 → 应转向模板工具，整个产品方向要重估 | 5 次访谈 |
| H2 | 用户愿意被追问 15-20 个问题，而不是想一次性说完 | 如果耐心只有 5 题 → 需把七模块压到 2-3 题 | 5 次观察 |
| H3 | "未验证/计划中"徽标不会让用户觉得作品集"看起来很弱" | 如果用户因此删掉真实内容 → 需改为读者侧折叠或导出时才提示 | 3 次测试 + 成品评价 |
| H4 | 面试官会因为看到诚实的局限说明而加分 | 如果没有影响 → 局限区块可降级为可选 | 3 次面试官访谈 |
| H5 | 零素材用户愿意花 1 周去做练习项目，而不是放弃 | 如果不会 → 零素材路径应改为"引导去积累，本次不出作品集" | 5 次访谈 |
| H6 | 产品经理单岗位收缩后，仍有足够用户愿意用 | 如果太窄 → 需重新评估首个岗位选择 | 10 份需求验证 |

### 7.3 研究方案（最小可行）

**阶段一：问题验证（不做产品，只验证痛点）**

- 对象：6-8 名在校生 / 应届生，正在找产品岗，其中至少 3 人**没有实习经历**
- 方法：40 分钟半结构化访谈，不给看产品
- 核心问题：
  1. 你上次准备作品集/简历，卡在哪一步？给我看当时的文件
  2. 你手上有什么经历觉得"拿不出手"？为什么觉得拿不出手？
  3. 你被问过最难回答的追问是什么？
- 产出：验证或推翻 H1、H5；修正问题优先级
- 成本：约 1 周

**阶段二：可用性测试（有产品后）**

- 对象：5 名符合首期画像的用户
- 方法：给一个真实任务（"用你最近的一个课程项目做一份作品集"），旁观不干预，记录卡点
- 记录指标：
  - 完成率（能否独立走到导出）
  - 每个问题的平均停留时长（>60s 视为卡住）
  - 跳过率（某一题跳过率 >40% 说明题目设计有问题）
  - 事实检查面板打开率与处理率
- 产出：验证 H2、H3；定位具体题目问题
- 成本：约 1 周

**阶段三：成品检验（最关键）**

- 对象：3 名真实招聘方（产品岗面试官）
- 方法：给两份作品集（一份带徽标诚实版，一份移除徽标），让他们评价"你想面试哪一个，为什么"
- 产出：验证 H4。这是唯一能判断"诚实徽标是加分还是减分"的方法
- 成本：约 3 天

### 7.4 研究纪律

- 不虚构访谈记录。任何结论必须能指向具体的访谈对象编号和原话
- 访谈记录存 `docs/research/YYYY-MM-DD-访谈N.md`，脱敏后入库
- 如果 H1 或 H3 被证伪，**产品方向需重新评审，不得以"已经在做了"为由继续**

| 阶段二 可用性测试 | ⬜ 未开始（产品已可测） |

## 14. 术语表

| 术语 | 含义 |
|---|---|
| **事实状态（claim status）** | 每条陈述的可信度标记，六态：fact / evidence / claim / assumption / plan / unknown |
| **缺口（gap）** | 用户跳过或答不出的问题，记入清单待回补 |
| **缺口驱动（gap-driven）** | 按"还缺什么"决定下一步，而非按固定字段表 |
| **方法论卡（playbook）** | 针对某类问题的 7 问结构化方法说明 |
| **ledger** | 全量陈述的可信度清单，导出前检查 |
| **练习路径（practice）** | 零素材用户的"真做一次"路径，含周期、步骤、产出证据 |
| **深流程 / 基础流程** | PM 走七模块深流程；其他方向走 5 步基础流程 |
| **事实闸门** | 导出前强制过一遍 ledger，未确认项需用户处理 |

## 15. 结语：这份文档的约束

写这份 PRD 时遵守了以下约束，便于你检验其可信度：
