## 1. 产品层面的核心问题（不是 Bug，是定位）

### P-1【已验证】产品在解决"排版"，用户真正的困难在"素材与证据"

现有 8 个功能模块里，5 个（主题、主色、Bento 布局、就地编辑、PDF 导出）服务于"**生成一份好看的文档**"；只有 1 个（素材盘点）服务于"**我到底有什么可展示的**"；**0 个**服务于"**我说的这件事是否有依据**"。

代码证据：`profile` schema 中所有指标都是 `{value, label}`（`renderer.js:432`、`wizard-engine.js:741`）。没有 `source`、`status`、`verifiedAt` 任何字段。也就是说，**系统在设计上就无法区分"用户算出来的数"和"用户编的数"**。

后果：产品可以帮用户做出"看起来专业"的作品集，但无法帮用户做出"经得起追问"的作品集。而后者才是招聘方的评价标准。

### P-2【已验证】"一次只问一个问题"被执行成了"单线程表单"，而不是"有记忆的访谈"

现有实现是：`nextStep(profile)` 用 **profile 的填充状态** 反推下一步该问什么（`wizard-engine.js:380-452`）。这带来两个真实缺陷：

1. **没有"已答记录"**。用户答过的内容只以最终字段形式存在，问题本身不被记录。所以无法实现"我问过你、你当时说不知道"这种状态，只能靠 `__detailDone` / `__metricSkipped` / `__linkAsked` 这三个下划线私有标记硬编码绕过（`wizard-engine.js:467,482,595`）。
2. **跳过 = 永久丢失询问意图**。`__metricSkipped` 一旦置真，该条目的数字题**再也不会被问**，即使用户后来想起了数据。这与"允许跳过但记录未解决内容"的要求正相反。

### P-3【已验证】零经历路径存在阻断性缺陷，用户会被卡死在第一题

这是本轮最重要的发现。完整运行输出：

```
[1] 零经历 hasExp 后: {noExp:true, srcScanned:true}
[1] 下一题: buildProject  "没关系，我们从零造一个出来"
[2] 选 starter 后下一题: exp.org  "先说第一段经历：在哪家公司 / 哪个组织？"
    skippable=false   targetType=experience
```

**用户刚刚说了"我什么都没有"，系统紧接着强制问"你在哪家公司"。** 而且 `skippable=false`，唯一出路是捏造一个机构名。

原因：`applyAnswer` 的 `buildProject` 分支只 push 了 project（`wizard-engine.js:529`），但 `nextStep` 里"经历优先于项目"（第 401-440 行在项目之前遍历 experiences，且 `!p.meta.expDone` 就要求新增经历）。`meta.noExp=true` 这个信号只在 `stepNoExperience` 里用过一次，之后**再没被任何逻辑消费**。

这条缺陷同时击中三件事：零经历用户（MVP 目标用户之一）走不通、产品被迫诱导编造、PRD 里"零经历能走完"的验收项不成立。

### P-4【已验证】"不编造"停留在横幅上，没有落到机制上

四个具体表现：

| 表现 | 代码证据 | 实际后果 |
|---|---|---|
| 任何文字都被当作指标 | `parseMetricInput('不知道')` → `[{value:'不知道',label:'效果'}]` | "不知道"会被渲染进 Bento 数据块的高亮位（`renderer.js:440` 会把首数字加 `<em>`），视觉上像一条成果 |
| "约"字被吞掉 | `parseMetricInput('提升约30%')` → `{value:'30%'}` | 用户明确表达的"不确定"在存储时消失，导出后变成确定数字 |
| 岗位库直接教用户写假数据 | `role-kit.js:25` 产品经理 starter："写一份 3 页的产品分析" | 不区分"分析"与"验证"，用户容易把分析结论说成用户验证结果 |
| 数字题提示语在诱导 | `wizard-engine.js:205`："哪怕只是大概的估计也很有价值" | 与"没有数据允许留空"冲突 |

### P-5【已验证】岗位知识库是词汇表，不是方法论

`role-kit.js` 每个岗位 5 个数组（tools/methods/metrics/tasks/starter）。以产品经理为例：
- `methods` 是 10 个名词（"竞品分析"、"A/B 实验设计"…），**没有**"它解决什么问题/需要什么前提/能产出什么证据/什么时候不该用"。
- 用户点一下 `+ A/B 实验设计` 就写进"做法"里（`index.html:526-534`），但系统不问他"你真的跑过实验吗、样本量多少、结论显著吗"。
- `starter` 是全库唯一的"如何从零开始"指导，且只有一句话。

这是**最容易造成"看起来会、一追问就露"**的设计。

### P-6【已验证】同一套流程服务 10 个岗位 = 没有一套是真的好

`stepTargetRole()` 列出全部 10 类岗位（`wizard-engine.js:47`），后续所有问题共用同一套字段（company/role/highlights/metrics）。产品经理需要的"用户是谁、证据是什么、为什么不做 B 方案"和设计师需要的"信息架构、可用性测试结论"完全不同，现有 schema 一个都装不下（`emptyProject()` 只有 name/role/period/context/problem/approach/result/metrics/tags/link/cover）。

按 MVP 要求缩到「PM / AI PM」不是砍功能，而是**终于可以给一个岗位设计对的问题**。

## 2. 技术风险清单

### R-1【已验证】回退机制语义不一致，会产生"幽灵状态"

`index.html:593` 每次前进把整个 profile 深拷贝压栈，`back()`（第 605-611 行）整体恢复。问题：
- `hist` 里存的是**不含步骤上下文**的快照。回退后 `goNext()` 重新用 `nextStep(profile)` 推算，可能算出**另一个问题**（因为 `__metricSkipped` 等标记也被回滚/保留，行为取决于具体时序）。
- `persist()` 把 `hist` 写进 localStorage 并只保留最后 60 条（第 314 行）。刷新后 `hist` 仍在，但用户已不记得自己回退到哪，`btnBack` 可能一点就跳到很早的状态。
- 空 `state.hist` 时 `btnBack.disabled=true`（第 446 行），但首次加载 `hist` 可能不为空 → **打开页面就处于"可回退"的诡异状态**。

判断：不是崩溃级 Bug，但会让用户"改着改着内容变了"。属于**P0 级的数据一致性风险**，因为整改后要引入"证据/状态"字段，回退若不同步回滚这些字段会产生更严重的错配。

### R-2【已验证】URL 与 CSS 注入未防护

| 项 | 证据 | 影响 |
|---|---|---|
| `javascript:` 链接直通 | `renderer.js:512` 只做了 `esc()`，产出 `href="javascript:alert(1)"` | 导出的 HTML 被点击即执行脚本；这是**导出物**，会被用户发给 HR |
| `meta.accent` 未校验直接拼进 `<style>` | `renderer.js:140` `--accent:${accent};` | 任意 CSS 注入，可隐藏内容、加载外部资源 |
| `x.cover` 图片地址未限制协议 | `renderer.js:494` | 可指向任意域名，导出后成为追踪像素 |

`esc()` 本身实现正确（`renderer.js:48-52`，五字符全转义），所以**文本 XSS 是安全的**——问题只在 URL 与 CSS 变量这两个"非文本通道"。

### R-3【已验证】"事实状态"完全不存在的数据结构

```
Profile v2 实际字段：meta / hero / metrics[{value,label}] / experiences[] / projects[] / skills / education / extras
```
要找的东西一个都没有：`evidence`、`claimStatus`、`source`、`verified`、`contribution`（个人贡献）、`aiAssisted`（AI 辅助标记）、`limitations`（局限）。
项目对象有 `context` 字段但**向导从不提问它**（`_nextProjStep` 第 479-488 行没有 context 步骤），所以渲染出的 `.proj-ctx` 永远为空。

### R-4【已验证】数据删除与留存控制缺失

- 无"删除全部数据"入口（只有「重来」清 profile，不清 `pf.ai.v3` 的 API Key）。
- 无 `beforeunload` 保护，关掉标签页就等于丢失当前未提交的输入。
- API Key 明文存 localStorage（`index.html:747`），**这是纯前端架构的固有风险**：任何同源 XSS、任何浏览器扩展、任何共用电脑的人都能读走。PRD 第 179 行写"Key 不上传"是正确的，但 `index.html:241` 对用户说"Key 只保存在你本机浏览器，不上传任何服务器"——**这句是准确的但不完整**，缺"因此它不安全"的提示。

### R-5【待检查】PDF 导出

`index.html:680-709` 逻辑为：向 iframe 写入无动效文档 → `html2pdf().from(d.body).save()` → 失败降级 `print()`。
待检查项（需真实浏览器 + 长文档）：① 超过 8 页时 `pagebreak.mode:['css','legacy']` 是否切断卡片；② 中文字体在 canvas 截图中是否完整；③ `scale:2` 在 3 个以上项目时是否 OOM；④ 失败时 `print()` 是否被弹窗拦截。
**本轮不宣称 PDF 可用或不可用。**

### R-6【已验证】LLM 是"半截功能"，且隐私口径与实现不符

- `Interview` 引擎内部有完整 `callLLM`（`interview-engine.js:552-580`，含 `response_format: json_object`、错误处理、JSON 容错解析）。
- **但 `index.html` 从未调用 `Interview`**——全文无 `Interview` 字样。也就是说用户填了 API Key，除了右上角开关变绿（`index.html:712-716`）之外，**没有任何一次请求被发出**。
- 反过来说：目前**没有**"LLM 覆盖事实"的风险，因为根本没有写入路径。整改时若要把 LLM 接进来，必须先建好"事实状态 + 用户确认"闸门，**否则接一个就会污染一片**。

### R-7【已验证】模块职责重叠

| 重叠点 | 说明 |
|---|---|
| `emptyExp/emptyProj` 两份 | `renderer.js:36-41` 与 `wizard-engine.js:672-677` 各定义一次，字段顺序和默认值靠人工同步 |
| `esc()` 两份 | `renderer.js:48`（完整五字符）与 `index.html:308`（缺 `>` 和 `'`）—— `index.html` 那份用于 toast/link 卡片，**漏掉 `'` 会在 HTML 属性里留下缺口** |
| 追问逻辑两套 | `interview-engine.js`（权重评分完整度）与 `wizard-engine.js`（状态机）都能决定"问什么"，但只有后者被使用；前者 39KB 代码成为死重量 |
| 岗位匹配仅供向导用 | `role-kit.js` 的 `starter` 在"零经历"文案里被当作正片展示，但代码里它是 `slice(0,60)+'…'`（`wizard-engine.js:106`），**建议正文被截断** |

## 4. 最重要的五项整改任务（按依赖顺序，不可并行乱序）

### T1 · 建立"事实状态"数据层（改造基础，必须先做）

**为什么排第一：** 后面 4 项全部要写这个字段。先做界面、后加字段，等于所有界面要重写两遍。而且它是唯一一项"做错会污染已有数据"的改动，必须最先定 schema 并写好迁移。

- 新增 `claim` 结构：`{ text, status, evidence[], contribution, source, updatedAt }`
- `status` 枚举（严格互斥）：`fact`（用户确认发生）/ `claim`（用户陈述未核实）/ `evidence`（有材料支撑）/ `assumption`（假设）/ `plan`（未来计划）/ `unknown`（信息不足）
- 所有 `metrics` 元素从 `{value,label}` 扩为 `{value,label,source,status,note}`，保留旧字段兼容
- 迁移：`meta.version: 2 → 3`，读旧数据时把所有指标标为 `claim` 并提示"这条数字还没有来源，补一下？"

**验证：** 老 localStorage 数据能无损升级；新数据无法在没有 status 的情况下被写出（用一个 `assertClaim()` 守卫）。

### T2 · 重构流程引擎：从"字段驱动"改为"缺口驱动 + 已答记忆"

**为什么排第二：** 它承载 T1 的所有写入，并且要修掉 P-3（零经历卡死）和 P-2（跳过即丢失）。不改它，T1 的字段永远填不上。

- 引入 `session`：`{ answers:[{stepId,targetPath,status:'answered'|'skipped'|'unknown',at}] }`，与 profile 并列持久化
- `nextStep` 的优先级从"字段空不空"改为"**未解决项 + 权重**"，并显式消费 `meta.noExp`（零经历时**跳过经历区块**，直接进项目构建）
- 跳过不再置 `__xxxSkipped`，而是记一条 `status:'skipped'`，在"缺口清单"里长期可见、可随时回来补
- 回退改为"按 answers 栈回放"，而不是 profile 快照，保证回退后问题序列一致

**验证：** 回归测试覆盖 ①零经历全程走通且**不出现 exp.org** ②每条跳过项在缺口清单中出现 ③前进 5 步再回退 5 步，问题序列完全一致。

### T3 · 收缩到「产品经理 / AI 产品经理」单岗位深流程

**为什么排第三：** 依赖 T1（要用新字段装"用户/证据/取舍"）、T2（要用新引擎跑分支）。这是降低后续所有工作量的关键一刀。

- 画像维度扩为 PM 专属：`{ 求职阶段, 是否有产品实习, 目标公司类型, 是否做过 AI 相关 }`
- 项目案例 7 模块（问题发现/问题分析/方案设计/个人贡献/验证结果/复盘/局限）成为**主 schema**，其他岗位暂时复用同一 schema（字段会显得不贴，但可接受）
- 保留 `role-kit.js` 的 10 岗位数据，但**只把产品经理那组升级为"方法论卡"**（每张卡含 7 问：解决什么问题/适用场景/前提条件/怎么执行/产出证据/何时不适用/无数据时怎么办），其余 9 个降级为"仅技能选项"
- UI 上的岗位选择改为"产品经理（深度）/ 其他岗位（基础）"两个入口，并明写差异

**验证：** 10 份产品经理知识卡全部具备 7 个字段且内容可评审；向导在 PM 路径下产出至少 1 个含 7 模块的完整案例。

### T4 · 事实核验闸门（把 P-4 落成功能）

**为什么排第四：** 需要 T1 的字段 + T3 的模块定义。

- **写入闸门**：任何进入 `result` / `metrics` 的内容，必须带动 `status`；无 status 的一律按 `claim` 处理并显示为"待确认"
- **解析收紧**：`parseMetricInput` 遇到不含数字的输入 → 不生成 metric，改为提示"没有数字也可以，要不要写一句定性结果？"；保留"约/大概/左右"进 `note`
- **导出前检查**：生成一份"事实清单"，逐条列 `claim` 与 `assumption`，让用户逐项确认或标为"未验证"；`unknown` 项直接标红
- **AI 边界**：LLM 只能提出**建议**并落为 `status:'assumption'` 草稿，**禁止**直接写 `fact`；用户必须逐条采纳

**验证：** 构造测试用例：`parseMetricInput('不知道')` 返回空；导出时存在 `claim` 项会弹检查面板；LLM 返回的字段落盘后 status 必为 `assumption`。

### T5 · 剪掉首期不承担价值的功能 & 补上隐私/删除

**为什么排第五：** 前四项完成后才知道哪些是死重量。而且删减会改动大量 UI，必须等核心流程稳定后再做，否则反复改。

- 裁剪/降级：主题 4→2、主色 6→1、手机预览删、`r.jina.ai` 网页代理**默认关闭**（只留 GitHub API）、`interview-engine.js` 判定去留（当前是死代码）
- 补上：删除全部数据、导出前隐私提示、API Key 风险说明、`beforeunload` 保护
- 保留不动：`renderer.js` 渲染、`inline-edit.js`、GitHub 链接读取、HTML 导出（都是稳定且成本低的）

**验证：** 首屏可交互元素数量下降 ≥30%；localStorage 清空后无残留 key；关闭代理后无任何外部请求（用 DevTools Network 截图为准）。

## 6. 对原设想的直接反驳

| 原设想 | 我的判断 | 理由 |
|---|---|---|
| "作品集生成是最终交付能力，也是产品价值" | **反对** | 生成能力是 commodity（模板站、Canva、Notion 都有），且做得再漂亮也不产生差异化。价值应该落在"证据的完整性"上——而这恰恰是现有代码 0 实现 |
| "一次只问一个问题" | **部分反对** | 单线程对零基础用户友好，但对"已有项目文档"的用户是折磨（他们想粘贴一整段）。T2 的 session 化就是为了让"逐题"和"批量导入"共用一套缺口模型，而不是二选一 |
| "保留 10 岗位知识库" | **反对首期保留** | 10 个岗位 × 每个 5 个数组 = 表面完整、实际都无法承载深流程。按 T3 收缩，其余降级为"仅技能选项"，成本几乎为 0，但避免了"看起来全面、处处不深" |
| "导出 PDF 必须真导出" | **同意，但不该是首期重点** | 如果内容不可信，导得越漂亮越危险。T4 的导出前检查优先于 PDF 美化 |
| "数据不出浏览器" | **必须改写** | 有 GitHub API 与 jina 代理两条外部请求。准确表述应为"除你主动触发的链接读取外，内容不离开浏览器"，并在界面上逐次提示 |
